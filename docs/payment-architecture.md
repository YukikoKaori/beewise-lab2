# Final payment: dynamic VietQR and manual bank review

Final Firestore mode uses `manual_vietqr` for new connections. Its chat opens the proposed class and invoice from Firestore and never invokes payOS. Existing payOS invoices, webhook verification, classes and history remain on the legacy adapter. There is no migration or backfill.

1. Verified Google staff/admin issues one immutable proposal and invoice per eligible Final chat. This is the first class offer and price: Final has no earlier accepted class proposal to copy, and the tutor's public hourly fee is not the total class price. Rules bind the offer to its chat, active tutor, operator recipient and unique transfer reference, and bound the VND amount. Parents cannot issue or reprice it.
2. The parent explicitly confirms the displayed VND total before seeing the QR. The acceptance transaction records the amount shown; Rules reject any amount other than the immutable offer amount. The parent can copy recipient, amount and reference. The invoice survives restart. A transfer claim moves the invoice to staff review and grants no class access.
3. Staff opens the actual recipient bank transaction history for the invoice shown, matches the posted credit, and enters the exact amount, reference, recipient BIN and account number, and a unique bank transaction identifier. The Web form requires acknowledgment of the statement check. Rules match those values against the invoice; the audit is staff-only. Neither client queries the bank, and a claim or screenshot is insufficient.
4. One Firestore transaction writes the verified invoice, the immutable review receipt, the bank transaction reservation and the official class. Rules use `getAfter()` to reject incomplete or mismatched writes. Concurrent decisions, revoked staff, duplicate transaction IDs and verification by ordinary parents or tutors are denied. Staff are the trust boundary: Firestore can validate the match and reviewer identity but cannot prove that a reviewer actually saw a credit at the bank. Mobile reads the resulting class through its existing schedule.

`offered → awaiting_transfer → awaiting_verification → verified` is the success path. Review may instead produce `rejected` with a reason. Before expiry the parent can correct the claim against the same invoice and reference without transferring again; each claim gets a new review ID. Staff can cancel an eligible unverified invoice; expired invoices reject further parent actions. Financial fields remain fixed through all transitions.

The operator must privately configure `settings/paymentRecipient` with `bankBin` (six digits), `accountNumber`, `accountHolder`, and `instructions` (empty if unused). Client writes are denied; invoices snapshot the configured values. Missing/invalid settings block issuance. Production values must be confirmed against the recipient bank before use. No default recipient, payment credential, external QR image service or Firebase Storage is required.

The Android QR is encoded locally using the NAPAS dynamic account transfer format: `QRIBFTTA`, VND currency code 704, exact amount, invoice reference and CRC-16. The [NAPAS technical specification](https://www.kiemtrabank.com/documents/QR_Format_T%26C_v1.5.2_EN_102022.pdf) supplies the reference vector; the `qr` package renders the matrix. See the [validation report](test-report.md) for scanner coverage. No real bank transfer or production account configuration was authorized. Demo fixtures must never be used to send money.
