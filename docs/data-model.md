# BeeWise Final data model

Both clients use the default Firestore database in `beewise-lab-3`. App Check and Firebase Auth are separate gates: App Check verifies the app; Rules verify the caller and data. Local emulators do not prove production App Check enforcement.

## Role provisioning and migration

The first admin is an existing verified Google Auth identity provisioned by the authorized Firebase operator in the console. Verify the UID, provider, and email privately; then set only `users/{uid}.role=admin` (plus a non-sensitive display alias). No production admin is provisioned or named here. Subsequent admin changes must target another UID, validate the role, and record actor and server time; revoke by setting role back to user, then verify the signed-in browser loses staff access and Rules deny writes. Preserve a separate authorized operator audit trail for any manual console changes. Never provision privilege based on an email domain, tutor approval or a consultant custom claim.

Migration is additive and not run live. Dry-run an authorized read-only inventory, preserve all UIDs and IDs, and keep existing parent/tutor/consultant documents and ownership unchanged. Absent role documents do not promote anyone; the Final mobile client creates a user role on first authenticated routing, and the Web Admin rejects missing roles. Review the production rules diff before enabling Final mobile. Do not copy private data into a public listing: verify publication consent and public fields at the publish step. Approval grants workspace access; publication is a separate staff action.

Firestore indexes: announcement feed uses status + createdAt DESC; review history orders by createdAt within one owner's subcollection; existing chat index unchanged. Web dashboard uses three server-side counts. Existing legacy backend remains deployed/managed separately; Final review and announcement paths use no custom server.


In Final mode, Android stores generated bytes in a private, owner-scoped support directory. Firestore confirms only metadata. Opening a local report needs the original device and an installed PDF viewer; sharing grants the selected Android app access to a copy. Switching accounts discards in-flight results and hides prior reports. A missing local file can be regenerated from the tutor profile. No Storage bucket, server, or extra Android storage permission is required.
